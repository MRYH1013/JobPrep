# Java 后端
## Java 开发工程师|java|先给语言契约和对象模型，再用边界案例验证，而不是只背实现细节。
equals 和 hashCode 为什么要一起设计？|相等对象必须产生相同哈希值，但哈希相同不代表相等。把可变对象作为哈希键时，修改参与计算的字段可能破坏后续查找。|不要把哈希冲突当成 equals 相等。|使用订单对象作 Map 键需要注意什么？
HashMap 为什么不适合并发写？|HashMap 没有提供并发写所需的同步语义。共享更新应选择合适的并发容器或外部协调，并注意复合操作仍要保持原子性。|换成并发容器也不代表任意多步逻辑都原子。|先判断不存在再插入应如何写？
String 为什么适合设计成不可变？|不可变值便于共享和推理，适合作为键与跨线程传递数据。频繁拼接仍需观察编译优化和实际分配，循环场景可以考虑可变构建器。|不可变不代表使用它的整个对象都线程安全。|循环拼接大文本怎么评估成本？
受检异常与运行时异常应该如何使用？|围绕调用方是否能合理恢复设计异常契约，保留根因和上下文，在适合的边界转换或处理。避免层层吞掉异常掩盖失败。|记录日志后继续返回成功会制造假成功。|批量任务部分失败怎样返回结果？
try-with-resources 解决了什么问题？|让实现 AutoCloseable 的资源在离开作用域时自动关闭，多个资源按逆序释放。业务仍需处理主异常及关闭阶段的附加异常。|不能把自动关闭理解成异常已经被处理。|关闭时再次抛异常会发生什么？
泛型擦除会带来哪些限制？|Java 泛型主要在编译阶段检查，运行时通常不能直接区分完整类型参数。需要运行时类型信息时显式传入 Class 或其他类型描述。|不能用 instanceof List<String> 判断元素类型。|反序列化泛型集合怎样传递类型？
集合遍历中删除元素有哪些安全方式？|按集合契约使用迭代器删除、removeIf 或生成新集合。并发场景还要理解一致性模型，避免假设迭代一定反映所有实时变化。|失败快速检查不是线程安全保障。|大集合删除的时间与内存成本如何比较？
## Java 并发工程师|concurrent|画出线程交错，明确可见性、原子性与资源上限，再给压力验证方案。
volatile 能保证计数自增原子吗？|volatile 提供相应可见性与有序性语义，但自增是读取、计算、写回的复合过程。计数应使用原子类、锁或适合场景的分段累加。|可见性不能替代复合操作原子性。|需要严格读取瞬时计数时如何选择？
synchronized 与 ReentrantLock 怎样选？|二者都可提供互斥；根据可中断获取、超时尝试、多个条件队列和代码复杂度选择。显式锁必须确保在 finally 中释放。|不要只用过时的绝对性能结论做选择。|获取锁超时后业务应怎样返回？
线程池提交任务的处理顺序是什么？|通常先建立核心工作线程，再尝试入队，队列满后尝试扩容，无法接收才触发拒绝策略。参数应结合任务耗时和服务资源测量。|无界队列可能把过载转化为内存与延迟问题。|拒绝时为什么不能直接丢弃支付任务？
ThreadLocal 在线程池里有什么隐患？|工作线程会复用，上个任务的上下文可能留给后续任务。按任务边界设置并在 finally 清理，避免数据串用和长期引用。|弱引用并不能替代业务主动清理。|异步跨线程如何传递追踪上下文？
CAS 为什么可能遇到 ABA 问题？|某值从 A 变 B 再变回 A，单纯比较当前值不能察觉中间变化。需要关心变化历史时引入版本戳，并处理重试与竞争成本。|无锁算法不等于没有竞争或一定更快。|版本号溢出和对象回收需要考虑什么？
Java 21 虚拟线程能否加速所有任务？|虚拟线程有助于大量等待型并发任务降低线程管理成本，不会增加 CPU 算力。仍需限制数据库连接和外部服务并发，行为应按 JDK 版本验证。|不要把线程更便宜理解成下游资源无限。|CPU 密集型任务如何设定并行度？
如何排查线程死锁？|采集线程栈，寻找等待关系与持锁关系的环，再核对锁顺序、超时与资源获取路径。修复后用可重复竞争场景验证。|仅重启服务无法消除产生死锁的条件。|怎样从设计上统一资源获取顺序？
## Spring 工程师|spring|说明代理、容器与事务边界，用实际调用链解释生效条件。
依赖注入为什么有助于测试？|通过构造器显式声明协作者，测试可替换外部依赖并检查边界行为。容器管理创建过程，业务对象不必自行查找服务。|依赖注入不等于所有对象都必须交给容器。|构造器参数过多说明什么？
Spring 代理模式下事务为何可能不生效？|事务拦截依赖调用经过代理；同对象内部调用等路径可能绕过拦截。核对代理类型、方法可见性、异常处理和事务管理器。|只加注解并不能保证任意调用路径都有事务。|如何通过拆分服务明确事务边界？
事务异常被捕获后为什么可能没有回滚？|框架依据穿过事务边界的异常及回滚规则决定处理。捕获异常并正常返回可能隐藏失败；需明确传播或标记回滚。|不要为了触发回滚把所有异常都改成同一种。|内层已标记回滚，外层继续提交会怎样？
REQUIRED 与 REQUIRES_NEW 的资源代价是什么？|REQUIRED 通常加入现有事务，REQUIRES_NEW 创建独立事务并挂起外层上下文。后者可能需要额外连接，必须评估连接池和锁等待。|独立事务不等于能无成本消除一致性问题。|审计日志与业务失败如何隔离？
为什么推荐构造器注入？|必要依赖在创建时完成，便于不可变设计和独立测试，缺失依赖更早暴露。可选依赖应通过明确契约表达。|为了方便测试反射写字段会掩盖依赖结构问题。|循环依赖暴露了怎样的设计信号？
Spring Bean 生命周期应该关注哪些边界？|区分实例化、依赖填充、初始化、代理包装与销毁，初始化时避免假设全部外部服务就绪。关闭阶段释放线程池和连接。|在构造器里做重型网络操作会增加启动脆弱性。|怎样设计应用优雅停机？
接口层与服务层的校验怎样分工？|接口层检查请求结构与基础约束，服务层维护跨入口一致的业务不变量。数据库约束为并发冲突提供最终保护。|只依赖前端校验无法保证业务正确。|两个并发请求都通过余额检查怎么办？
## 数据库工程师|mysql|给出 SQL、数据规模、隔离级别与执行计划，再讨论验证和回滚。
联合索引的列顺序怎样决定？|结合等值过滤、范围、排序与返回列设计候选索引，观察数据分布及执行计划；优先服务真实高价值查询。|范围后的列并非在所有意义上完全无效。|何时覆盖索引仍不值得建立？
MVCC 与范围锁怎样分工？|一致性读依赖版本可见性，锁定读要按隔离级别和访问路径加锁。先区分读的类型，再讨论幻读与冲突。|不要把所有 SELECT 都当成同一种读取。|同一事务混用两类读有什么风险？
慢 SQL 应该先看哪些证据？|从慢日志和业务链路定位语句，检查执行计划、扫描行、锁等待和返回数据量。用代表性参数验证，而不是凭语法猜测。|优化一个样本参数可能伤害另一类查询。|如何评估上线索引的风险？
覆盖索引为什么可能减少查询成本？|查询所需列能从索引获得时，可能减少访问聚簇记录的次数。收益取决于计划、返回范围与索引大小，也会增加写入维护成本。|不要为了覆盖任意查询堆积超宽索引。|宽字符串列纳入索引有哪些代价？
数据库死锁应该如何处理？|保留死锁日志和事务访问顺序，统一锁定顺序、缩短事务并减少扫描范围；业务对可重试失败采用有界重试。|死锁不能只靠增加锁等待时长解决。|重试时如何避免重复扣款？
深分页为什么可能越来越慢？|大偏移查询可能先扫描并跳过大量记录。稳定排序下可用游标条件从上次位置继续，同时处理相同排序值与数据变化。|游标分页不天然支持任意跳页。|排序列重复时怎样设计游标？
乐观锁怎样避免库存超卖？|用带版本或剩余库存条件的更新原子判断是否成功，以影响行数确认结果。竞争失败应重试或提示，扣减与订单需要明确事务边界。|先查库存再无条件写回并不安全。|热点商品竞争高时如何减少重试？
## 缓存工程师|redis|区分缓存性能与数据正确性，推演过期、失败、恢复与并发读写。
缓存穿透、击穿、雪崩有什么区别？|分别关注无效键反复访问、热点键失效和大面积集中失效。可组合输入过滤、短期负缓存、请求合并、过期抖动与降级。|负缓存需要控制时长，防止屏蔽刚创建的数据。|布隆过滤器存在误判时如何处理？
缓存与数据库一致性怎样设计？|先明确可接受的不一致窗口。常见旁路缓存写入先更新数据库再失效缓存，配合可靠重试与版本控制；关键强一致读取需另行设计。|延迟双删不能保证所有故障与交错下的强一致。|删缓存失败如何确保最终修复？
RDB 与 AOF 如何取舍？|RDB 侧重快照，AOF 记录写入操作，恢复窗口与成本依配置及故障而变。结合恢复时间和数据丢失目标选择，并定期演练。|开启持久化不代表绝不丢数据。|备份能否在另一台机器恢复？
Redis 内存淘汰与过期有什么不同？|过期按键的有效期清理，淘汰在内存压力下依据策略选择数据。监控命中率、淘汰数和内存，避免业务误依赖缓存永久存在。|设置 TTL 不代表到期瞬间所有内存立即释放。|重要数据为什么不应只保存在易淘汰缓存？
分布式锁的释放为什么要比较持有者？|租约到期后可能已有新持有者获得锁，旧请求直接删除会破坏互斥。比较 token 和删除应原子完成，资源侧还需防止过期持有者写入。|续租不能覆盖所有进程暂停与网络故障。|fencing token 应由谁检查？
大 key 与热 key 应怎样区分？|大 key 关注单键大小和操作成本，热 key 关注访问集中度。分别采集大小分布、延迟和流量，选择拆分、异步删除或本地缓存等方案。|平均流量无法揭示少量极热键。|本地缓存怎样控制失效扩散？
Redis 用作限流器应考虑什么？|明确按用户、接口还是租户计数，选择固定窗口、滑动窗口或令牌桶。原子执行更新，并决定服务故障时放行还是拒绝。|单实例原子性不能自动解决跨分片全局限额。|窗口边界突发怎样平滑？
## 后端架构工程师|architecture|先定义业务不变量、流量和故障目标，再推导架构与可观测指标。
消息重复消费如何保持幂等？|为业务操作选稳定幂等键，用唯一约束或状态机原子接收，再执行可恢复流程。对外部副作用保留操作记录并设计补偿。|先查后写的去重在并发下可能失效。|幂等记录保留多久合适？
消息如何避免发送成功但业务回滚？|将业务变更与待发送事件放进同一本地事务，通过 outbox 转发并重试。消费端仍需去重，监控积压与最终送达。|outbox 解决的是边界协同，不意味着恰好一次。|转发后未标记完成就崩溃怎么办？
超时与重试为什么可能放大故障？|上游超时不等于下游停止，多个层级同时重试会放大负载。统一超时预算，采用有界重试、退避与抖动，并仅重试适当失败。|所有错误都立即重试会加重雪崩。|付款超时但已扣款如何查询与恢复？
接口幂等键应怎样设计？|让一个明确业务意图对应稳定键，并关联请求摘要、处理状态与结果。冲突请求不能悄悄复用另一个操作的成功结果。|每次重试随机生成新键无法实现去重。|请求参数变化但幂等键相同时怎么办？
系统容量估算应该从什么开始？|从业务峰值、请求扇出、数据增长和单操作成本推算，再用压测验证瓶颈。保留余量并关注尾延迟与故障降级容量。|平均 QPS 不能替代峰值与突发模型。|单个依赖变慢会怎样影响并发数？
线上延迟突然升高如何排查？|先看影响范围与变更，分解入口、下游、线程池、连接池和数据库等待。用链路与指标定位，必要时先回滚或限流再深挖。|CPU 正常不代表系统没有资源等待。|如何区分处理慢和排队慢？
分库分表前需要回答哪些问题？|先确认瓶颈是否可用索引、归档或读写扩展解决；再决定分片键与迁移方案，评估跨分片事务、聚合和热点。|分片不只增加容量，也增加运维与业务复杂度。|更换分片规则怎样做到可回滚？
