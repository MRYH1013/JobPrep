# 游戏行业
## Unity 客户端开发|unity|以目标设备和帧预算为前提，结合 Profiler 证据说明生命周期、性能与工程取舍。
Update 与 FixedUpdate 如何分工？|按帧变化的输入和表现通常在帧循环处理，固定时间步用于物理相关更新。缓存输入意图并在适当时机应用，注意一帧可能发生零次或多次物理步。|固定更新频率不等于渲染帧率。|低帧率时角色抖动怎样排查？
频繁生成子弹为什么适合对象池？|复用已创建对象减少重复创建与销毁的成本；取出时初始化状态，归还时清理事件、计时器和引用，限制池容量。|池化会保留内存，不能无上限缓存。|子弹归还后旧回调仍执行怎么办？
如何定位 Unity 的 GC 尖峰？|在目标设备录制性能数据，关联分配与回收时间，定位高频临时对象、装箱和字符串构建。减少不必要分配后复测长时间稳定性。|编辑器结果不能直接等同玩家设备。|优化后内存更高但卡顿更低如何解释？
协程是否等于多线程？|协程按调度点分段执行，常见 Unity 协程仍在主线程推进。CPU 密集任务不能仅靠协程消除阻塞，异步任务访问引擎对象需遵守线程限制。|yield 不会自动把工作移到后台线程。|下载完成回调更新 UI 要注意什么？
物理射线检测怎样减少开销？|先明确检测频率与对象范围，利用层过滤和合适的查询 API，避免每帧大量无差别查询；根据需要复用结果缓冲。|减少次数不能牺牲关键碰撞的正确性。|高速物体穿透需要如何验证？
场景切换时怎样管理持久对象？|明确跨场景服务和场景局部对象的所有权，避免重复创建单例；卸载时解除事件和资源引用，异步加载要处理取消与重复请求。|DontDestroyOnLoad 不是通用内存管理方案。|切换十次场景如何检查泄漏？
帧率下降时先优化 CPU 还是 GPU？|先用性能轨迹与渲染统计区分瓶颈，观察主线程、渲染线程和 GPU 耗时，再针对脚本、绘制或带宽采取措施。|Draw Call 数量不是唯一性能指标。|分辨率降低后帧率明显提升说明什么？
## Unreal 开发工程师|unreal|先解释 Gameplay Framework 的职责，再按服务端权威与资源生命周期推导实现。
GameMode 与 GameState 有何不同？|GameMode 管理游戏规则并主要存在于服务端，GameState 用于表达可同步给客户端的局势状态。把客户端需要显示的数据放在合适的复制对象中。|不要假定客户端可以直接读取服务端 GameMode。|计分板数据应该放在哪个对象？
Pawn 与 PlayerController 为什么分离？|Pawn 表示被控制的实体，Controller 表达控制意图。分离后可以换角色、重生和切换控制目标，而不把全部身份逻辑绑在实体生命周期上。|角色死亡不一定意味着玩家身份消失。|观察者模式怎样切换控制？
属性复制与 RPC 各适合什么场景？|属性复制表达状态同步，RPC 表达远端调用或事件意图。选择可靠性和调用对象时考虑所有权、频率与带宽，不把高频表现全部变成可靠 RPC。|可靠 RPC 也不等于任意情况下都能立刻送达。|晚加入玩家如何获得当前局势？
网络游戏为什么强调服务端权威？|关键规则由服务端判定，客户端提交意图并预测表现；服务端验证输入、状态和频率，减少信任客户端结果造成的作弊空间。|只把伤害数值发给服务端并不安全。|如何平衡响应速度与校验成本？
行为树与状态机怎样选择？|状态机适合状态清晰的有限流程，行为树便于组合任务、条件与优先级。依据复杂度和调试需要选择，也可分层组合。|行为树并非所有 AI 问题的最优解。|被攻击时怎样打断巡逻？
蓝图与 C++ 的职责怎样划分？|稳定底层能力与性能敏感逻辑可用 C++，高频调整的玩法参数和编排可暴露给蓝图；建立清晰接口并通过性能数据验证。|不要把蓝图简单描述成不能用于正式项目。|策划频繁改规则如何减少程序依赖？
大世界资源加载怎样避免明显卡顿？|按玩家移动与可见范围组织加载，提前准备关键资源，限制同时激活的工作量；区分存储读取、反序列化与实例化成本。|异步加载不等于所有后续步骤都不会卡主线程。|高速移动时加载不及时怎样降级？
## 游戏系统策划|game-design|说明目标玩家、核心循环与约束，用可玩原型和数据检验设计假设。
如何定义一个游戏的核心循环？|描述玩家反复进行的行动、反馈和成长回报，说明每步提供的动机。先用最小原型检验循环是否成立，再扩展内容层。|堆功能列表不等于说明核心体验。|去掉奖励后玩法还吸引人吗？
战斗技能应该怎样平衡？|明确技能定位、资源消耗、风险与反制手段，比较不同场景下的收益。使用对局数据与玩家反馈，而非只比较伤害数值。|全局胜率相同不代表体验公平。|高手和新手使用效果差异很大怎么办？
游戏经济如何控制资源通胀？|画出资源来源、去向与库存变化，区分免费和付费人群，调整产出与消耗并观察长期净流入。避免用强制消耗破坏体验。|一次性活动消耗不一定解决长期供需失衡。|老玩家积累太多资源怎样过渡？
新手引导如何降低早期流失？|围绕核心操作逐步揭示信息，让玩家尽快体验价值；观察每步退出与失败，减少强制打断并给熟练玩家跳过路径。|完成引导不等于理解玩法。|怎样区分教程太难和节奏太慢？
付费设计怎样兼顾收入与玩家信任？|先定义可售卖价值与公平边界，清楚展示获得条件、价格和限制；观察长期留存与投诉，而不只优化短期转化。|不能用隐瞒规则或误导承诺提升转化。|强付费玩家影响普通玩家体验怎么办？
活动策划如何评估收益？|明确目标人群、回流或活跃目标、资源成本与奖励影响，比较基线和活动后变化。检查是否只是提前透支后续活跃。|活动参与人数不是唯一成功指标。|活动结束后留存下跌怎样分析？
一份系统策划案应该交付什么？|包含目标、规则、状态流程、数值、异常、UI 需求与验收标准；让程序、美术和测试对边界有共同理解。|描述理想流程而不写失败路径会增加返工。|规则中途改变时如何同步影响范围？
## 游戏关卡策划|level|从空间目标、玩家行为与反馈节奏出发，通过白盒和试玩迭代验证。
白盒关卡阶段应该验证什么？|优先验证路线、尺度、节奏和核心机制，而非美术完成度；记录试玩者犹豫、迷路和失败的位置，再修改空间。|设计者自己能通过不能证明玩家理解。|白盒测试应该记录哪些行为？
怎样引导玩家而不过度依赖箭头？|组合构图、光照、地标、声音和路径可达性形成线索；在关键分叉试玩验证，必要时保留可选辅助提示。|视觉引导不能替代通路可读性。|玩家关闭声音后还能辨认路线吗？
关卡难度曲线如何设计？|逐步引入机制，再在安全环境练习，随后组合和变奏。交替安排压力与恢复，按失败原因而非仅按通关率调整。|不断增加敌人数不等于合理难度成长。|老玩家觉得简单，新玩家觉得难怎么办？
多人地图怎样评估公平性？|评估出生点到关键区域的时间、视线、掩体和资源控制，结合不同阵营与水平对局数据寻找结构性优势。|几何对称不一定带来实际玩法公平。|一方胜率偏高怎样定位原因？
解谜关卡怎样避免依赖猜测？|先明确玩家需要形成的推理，保证线索可见、规则一致和反馈可理解。提示应逐层揭示，区分没看见与没理解。|谜底合理不代表推理过程充分。|玩家给出另一种合理解法怎么办？
关卡节奏如何与叙事配合？|用探索、挑战和休息区承载信息，避免战斗高压阶段塞入关键对白；允许不同游玩速度的玩家获得核心信息。|过场数量增加不代表叙事更强。|玩家跳过剧情怎样保持任务可理解？
关卡上线后怎样迭代？|聚合死亡、停留、退出与路径数据，结合录像解释原因，优先修复阻塞与误导。每次改动保留版本和回归路线。|热力图显示集中不自动意味着设计有问题。|怎样分辨探索停留和卡关停留？
## 游戏技术美术|art|以视觉目标、资产预算和运行平台为约束，展示制作与验证流程。
PBR 材质制作为什么要统一规范？|统一材质输入含义、贴图约定和校准环境，减少资产在不同灯光下失真。金属、粗糙度等参数应服务真实材质响应。|不能只在单一展示灯光下判断资产质量。|外包资产接入如何做检查？
LOD 如何在画质与性能间取舍？|根据屏幕占比和视觉重要性降低细节，检查轮廓、材质与切换突变，并在运动和多种距离验证。|面数下降不代表材质和绘制成本同步下降。|角色近景切换明显怎样改善？
透明特效为什么容易产生高开销？|重叠透明区域可能造成重复着色与混合，需观察屏幕覆盖率和过度绘制，减少无效区域与层数，控制材质复杂度。|粒子数量少也可能因覆盖屏幕而昂贵。|移动设备全屏技能怎样设预算？
贴图预算应该怎样制定？|按平台内存、分辨率、资产重要性与同时可见数量规划，采用适合的压缩和流式策略，实机验证清晰度与峰值占用。|磁盘文件小不代表运行时显存一定小。|如何处理近景角色与远景建筑的优先级？
骨骼动画怎样减少穿插和性能问题？|从绑定权重、骨骼数量、动作范围和更新频率协同检查，关键动作逐帧验证，远处角色可降低细节或更新成本。|只在静止姿势检查模型会漏掉动作问题。|换装后出现穿插如何定位责任边界？
技术美术如何搭建资产检查工具？|把命名、尺寸、材质、引用和预算规则自动化，输出可操作的错误报告，并允许有依据的例外流程。|工具只报失败却不解释位置会拖慢制作。|规则更新后旧资产怎样迁移？
美术效果与帧预算冲突时怎样沟通？|用实机数据解释主要开销，提出视觉影响不同的替代方案，与美术和程序一起比较。保留关键视觉目标，明确平台档位。|不能只用性能不够否定全部表现需求。|怎样证明简化后玩家感知影响较小？
## 游戏发行运营|steam|定义用户漏斗与数据口径，结合版本和渠道分析，区分相关性与因果。
愿望单数量能否直接预测游戏销量？|愿望单是兴趣信号，转化受到时间、地区、价格和来源影响。结合分群和历史转化估计范围，避免承诺固定转化率。|愿望单不是预售订单。|不同展会带来的愿望单质量如何比较？
游戏测试应该怎样收集有效反馈？|明确测试目标与招募条件，结合行为数据、访谈和问题复现信息。区分体验偏好、理解障碍和技术缺陷再排优先级。|最响亮的反馈未必代表主要玩家。|小样本负面意见如何判断是否值得改？
留存指标应该怎样定义？|明确起始事件、时区、用户身份和返回事件，分别看新用户与回流用户。按渠道和版本分群，避免把口径变化当作产品改善。|次日留存不能直接代表长期健康。|跨设备玩家怎样去重？
新版本发布如何降低运营事故？|准备发布清单、兼容性检查、监控和回滚方案，明确公告、客服与技术负责人。分批放量时观察错误、经济与关键路径指标。|发出公告不代表所有客户端已更新。|更新后存档不兼容怎么办？
差评突然增加应怎样响应？|先核实是否与崩溃、性能、规则或沟通有关，公开可确认信息和修复进展。把可复现问题送入跟踪，不与玩家争论。|删除不喜欢的反馈无法解决产品问题。|补偿方案如何避免产生新的不公平？
买量渠道怎样判断真实效果？|比较来源用户的留存、付费与回收周期，排查归因与异常流量。用可持续回报评估，不只看低安装成本。|短期付费峰值可能来自少数异常账户。|自然增长与广告增量怎样区分？
社区活动怎样兼顾活跃与秩序？|提前写明规则、资格、奖励与处理机制，保障不同玩家参与机会。收集质量与负面影响并复盘，不只追求发帖数量。|互动越多并不一定意味着社区更健康。|作弊刷奖励如何处理并解释？
